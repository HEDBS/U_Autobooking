# U_Autobooking · 浴室自动预约系统

作者：**HEDBS** ｜ 项目地址：https://github.com/HEDBS/U_Autobooking ｜ 许可证：MIT

针对 `h5.hydream.cn`（浴室预约系统）的自动预约工具。
**单个 .py 文件，双击运行，全程菜单操作，无需命令行参数。**

## 一、功能

| 功能 | 说明 |
|---|---|
| 条件① 排队人数 | 排队人数 ≥ 设定值时自动加入排队，并持续跟踪，排到位置后报告浴室与位置编号 |
| 条件② 定时预约 | 按计划洗澡时间判断何时抢空位、何时排队（保守策略，不会提前把你叫走） |
| 结果通知 | 预约成功后可将结果推送到指定命令（消息见环境变量 `HY_DREAM_MSG`） |
| 快速启动 | 配置完成后启动时自动倒计时进入监控，可按键中断 |
| 自检 | 内置 23 项离线自检，含 9 种完整流程模拟，不联网即可验证 |

判断方式**三选一（单选）**：条件① / 条件② / 不自动预约。切换时参数不丢失。

## 二、怎么用（三步上手）

### 第一步：双击运行

双击 `U_Autobooking.py`，会打开一个黑窗口。全程按数字选菜单，不需要敲命令行。

### 第二步：第一次运行，跟着引导填四项

第一次打开它会依次问你四件事，每项填完按回车：

1. **账号密码** —— 填浴室系统的账号（手机号）和密码。程序当场登录验证，不对会重问。
2. **目标浴室** —— 列表里带每间浴室当前的空闲数，例如 `1号楼1层 (男)   26/28`。
   直接回车 = 用你在网页上设的默认浴室；想换就输入序号，多间可以写 `1,3`。
3. **判断方式（只能选一种）**：
   - 选 `1` = **排队人数**：排队人数 ≥ 你填的数字时，自动去排队；
   - 选 `2` = **定时预约**：你告诉它打算几点洗，剩下的它自己判断；
   - 选 `3` = 先关掉，只看不预约。
4. **检测周期** —— 多久检查一次。默认 1 秒，直接回车。

填完进入主菜单。这些设置存在 `U_Autobooking_state.json`，下次打开不用再填。

### 第三步：启动

主菜单按回车（或按 `1`）开始监控。之后每一轮都会打印一行，说明现在什么情况、为什么还没动手：

```
第 12 轮：1号楼1层 (男) 空闲 3/28，排队 0 人 —— 未达条件（排队 ≥70）
```

条件满足时它自己动手，成功后会写明**哪间浴室、几号位置**。想停就按 `Ctrl+C`。

### 平时会用到的操作

| 想做什么 | 怎么做 |
| --- | --- |
| 换判断方式、改阈值、改洗澡时间 | 主菜单 `3`，选要改的那项 |
| 取消已经排上的队或预约 | 主菜单 `2`，它会先显示当前状态，再让你确认 |
| 检查程序本身有没有问题 | 主菜单 `4`（离线自检，不联网、不碰账号） |
| 不想每天开窗口 | 见「七、无人值守运行」 |

### 怎么看它现在的状态

- 主菜单顶部会显示目标浴室此刻的情况，例如 `实时状态（19:28:13）：空闲 26/28`；满员时显示当前排队人数。
- 运行时每一轮都会打印一行，写明空闲数、排队人数和判断结果。
- 完整记录在 `U_Autobooking.log`，记事本就能打开。

### 关于登录

登录成功后会把会话存下来，下次打开直接进去，不用重复输密码。会话失效了，程序会用保存的账号密码自动重登。
如果提示密码不对、或被要求 10 分钟后重试，进主菜单 `3 → 1` 重新填一次密码即可。

## 三、浴室如何选择（初始默认浴室）

站点数据结构为：**校区 → 设备类型 → 浴室（区域） → 位置**。程序的处理方式：

1. **校区**：自动使用账号中保存的校区（`default_org_area_id`）。未绑定校区时会提示先在网页端选择。
2. **设备类型**：列出该校区全部类型（浴室、吹风机等），默认选中「需要预约」的类型。
3. **浴室**：列表同时显示**空闲/总计**，便于直接判断。选择规则：
   - 标记「账号默认」的浴室 —— 网页端设置的默认浴室（`default_device_area_id`），**直接回车即选中它**，这是默认的初始浴室；
   - 没有账号默认时，回车沿用上次选择；
   - 无任何历史记录时，回车选中列表第一项；
   - 可多选，例如输入 `1,3` 同时监控两个浴室，任一满足条件即执行。
4. 选择结果保存至 `U_Autobooking_state.json`，后续无需重复设置；需要变更时进入设置菜单第 2 项。

## 四、预约判断方式（三选一）

自动预约的判断方式**只能选一种**，在「修改运行设置 → 3) 预约判断方式」里显式选择：

| 选项 | 触发规则 | 适合什么情况 |
| --- | --- | --- |
| 条件① 排队人数 | 排队人数 **≥ M** 时自动加入排队 | 你不急着洗，先去长队列里占位（**只支持「大于或等于」**） |
| 条件② 定时预约 | 按**计划洗澡时间**保守抢位 / 排队 | 你打算 X 点洗，让程序算好什么时候动手 |
| 不自动预约 | 关闭，程序只做监控不做任何预约动作 | 只想看情况、或临时停用 |

切换方式**不会丢失**已填的参数（排队阈值、计划时间都保留），随时可以换回来。

### 条件① 排队人数

`排队人数 ≥ M` 时自动加入排队。只提供「大于或等于」这一种比较方式：
排队人数越多说明轮到你越晚，所以这个条件是"提前去队列里占位"，而不是"抢位置"。
排队成功后程序会持续跟踪，轮到你时自动完成预约并报告浴室与位置编号。

该方式**不看时间**：只要排队人数达标就排队。M 不接受 0（`排队 ≥ 0` 恒成立 = 每轮都去排队），
填 0 会被拦下并提示。

### 条件② 定时预约（保守策略）

程序按你的计划时间自己判断"什么时候该动手"：

| 时刻 | 程序行为 |
| --- | --- |
| 未到该拿位置的时间 | **有空位也不抢** —— 抢到就必须立刻到场，早拿到等于浪费；只在「站点预计等待（按保守系数折算）能覆盖剩余时间」时才**提前排队占位** |
| 已到该拿位置的时间（计划时间 − 到场准备） | 有空位 → **直接抢位置**；已满员 → **加入排队** |
| 超过计划时间仍未拿到位置 | 到设定的放弃时限后停止，并自动退出排队 |

#### 为什么预计等待要打折扣

预计等待 **优先用站点给出的 `expectedWaitingTime`**。实测这个数字与排队人数不成正比
（151 人对应 30 分钟、139 人对应 50 分钟），拿不到时才退回 `排队人数 × 平均时长`，
再乘 **保守系数**（默认 0.8，故意低估等待 → 更晚排队 → 不会提前把你叫走）。

### 平均洗澡时长与性别

| 性别 | 内置默认 | 依据 |
| --- | --- | --- |
| 男 | 10 分钟 | 北京大学学报（自然科学版）2025：高校学生每周洗浴 4~6 次，25% 单次超过 20 分钟；新浪天津 2019 洗澡习惯报告：男性平均比女性少约 10 分钟 |
| 女 | 20 分钟 | 同上 |

**性别来源**：优先从账号读取（`getUserInfo` 的 `sex`，1=男 2=女），读不到时可手动指定；
同时用于 **校验浴室性别限制**（`gender_limit`）。

### 条件② 启动前的合法性检查

| 检查项 | 依据 |
| --- | --- |
| 距计划时间是否还有足够的到场准备时间 | 你设置的到场准备分钟数 |
| 计划洗澡时长是否超过站点单次上限 | 设备类型的 `max_run_time`（实测 60 分钟） |
| 浴室性别限制是否与你的性别一致 | 浴室的 `gender_limit`（实测 8 间均为男浴） |
| 浴室是否维护 / 停用 / 未开放 | 浴室的 `status` 与 `expected_open_time` |
| 每日预约次数上限 | 设备类型的 `max_reserve_times`（实测 10 次） |

### 侦测频率

默认 **1 秒 1 次**，可在 1~60 秒之间调整（设置菜单第 4 项）。每轮只发 **1 个总线请求**
（一次性拿到空闲数、排队人数、预计等待、本人状态），失败不在请求内重试、交给下一轮，被拦截时自动退避。

## 五、取消机制

排队或预约成功后可以退出，三个入口：

| 场景 | 行为 |
|---|---|
| 手动取消 | 主菜单 `2) 取消排队 / 取消预约`：先显示当前状态（如"排队中：当前排位 136 号"），确认后排队中调 `cancelQueue` 退出队列；已预约/使用中调 `cancelReserve` 释放位置，并复核结果 |
| 排到的时间早于计划 | 判断方式为定时预约时，排到太早会自动取消该位置并继续等待合适时机（默认开启）。为避免反复消耗每日预约次数，连续自动取消最多 3 次，之后保留位置并提示 |
| 超过计划时间仍未轮到 | 自动退出排队（默认开启），避免占着队列却已不打算去 |

取消后主页面"实时状态"会立刻显示 `已无排队/预约` 作为复核。

## 六、生成文件

| 文件 | 说明 |
|---|---|
| `U_Autobooking_state.json` | 账号密码、选择的浴室、判断方式与参数、登录状态。程序自动维护，无需手工编辑 |
| `U_Autobooking.log` | 运行日志，记录每轮的浴室空闲情况与操作结果 |

登录状态自动复用；失效时使用已保存的账号密码自动重新登录。
两个文件均为本机明文存储，请勿随意外传该目录。

## 七、无人值守运行

计划任务、后台启动（`pythonw`）等无键盘输入的环境下，程序自动跳过菜单，
直接以已保存的配置开始监控，无需任何人工操作。

## 八、排错

主菜单第 4 项「系统自检」离线检查接口解析、判断逻辑、浴室状态、排队数据、登录状态存取，
以及 9 种完整流程模拟，还会核对程序自身有无缺失的函数、各设置界面能否正常打开。不联网、不涉及账号。

| 现象 | 处理 |
|---|---|
| 账号或密码不正确 | 设置菜单第 1 项重新输入 |
| 站点提示"为了保护您的账户安全，请10分钟后重试" | 站点对连续输错密码有 10 分钟限制；无人值守时程序会按提示等待后重试 |
| 请求被网站安全策略拦截 | 通常稍后自动恢复；持续出现请调大检测周期 |
| 101212 你同时只能使用一台设备 | 你的账号已有一台设备（预约中或使用中）。程序会自动识别并跳过重复预约，主页面的"实时状态"能看到当前占用（如 `你 已预约：1号楼1层 位置 22`）；等该设备结束或先手动停止后再抢 |
| 反复提示登录状态失效 | 设置菜单第 1 项重新输入密码（会清除旧登录状态） |
| 需要完全重新配置 | 删除 `U_Autobooking_state.json` 后重新启动 |
| 双击文件打开的是其他软件 | 设置菜单第 5 项「启动方式修复」 |

## 九、技术说明

站点为 pgel 框架的 H5 应用，接口为 `POST https://lz.hydream.cn/api/v1/<模块>/<动作>`，表单提交。

| 用途 | 接口 | 关键参数 |
|---|---|---|
| 登录 | `UserApi/loginWidthPwd` | `mobile`、`pwd`（返回 `sessionName`/`sessionId`，配合 cookie 维持登录） |
| 账号信息 | `UserApi/getUserInfo` | — |
| 设备类型 | `DeviceAreaApi/selectDeviceTypeByOrgAreaId` | `orgAreaId` |
| 浴室列表与空闲数 | `DeviceAreaApi/selectDeviceAreasWithDeviceState` | `orgAreaId`、`deviceTypeKey`（返回 `idleNum`/`totalNum`） |
| 位置列表 | `DeviceAreaApi/selectDevicesByAreaId` | `deviceAreaId`、`deviceTypeKey`（`device_status=ready` 为空闲） |
| 实时状态总线 | `BusApi/exchangeMsg` | `deviceAreaId`、`deviceTypeKey`、`time`、`lastId`（返回 `waitingInfo` 排队人数、`userState` 本人状态） |
| 加入排队 | `DeviceAreaApi/queueUp` | `deviceAreaId`、`deviceTypeKey`（返回 `result=queued`） |
| 取消排队 | `DeviceAreaApi/cancelQueue` | 同上 |
| 体温登记 | `HealthApi/createLog` | `bodyTemperature`、`deviceTypeKey`（程序会先读取站点设置 `checkBodyTemperature`，仅在该校区确实需要时提交） |
| 预约 | `DeviceApi/reserve` | `uuid`（位置的 `device_key`） |

接口字段做了多命名兼容，站点版本差异一般不会导致失败。
运行环境：Python 3.7 及以上，仅使用标准库。

## 十一、已知取舍：为什么没有实现「暴力模式」

考虑到同时段可能有大量用户抢位置，曾评估过一种"暴力模式"：不等待返回、按固定频率
连续并发发送预约请求，直到成功为止。**当前版本不实现**，原因如下：

| 风险 | 说明 |
|---|---|
| 触发风控 | 站点前置阿里云 WAF，且存在登录频率限制（实测连续失败即被要求等 10 分钟）；并发请求是最容易被识别为攻击的特征 |
| 账号风险 | 高频异常调用可能导致账号被限制或封禁，得不偿失 |
| 无法判定结果 | 不等待返回就发下一次，无法知道哪一次成功，可能同时占住多个位置，触发 `101212 你同时只能使用一台设备`，或白白消耗每日预约次数上限（实测为 10 次） |
| 数据竞争 | 服务端分配位置存在竞态，暴力并发未必比"精准时机 + 高频轮询"命中率更高 |

**更有效的替代做法**（本程序已实现）：把轮询压到 1 秒并在每轮只发 1 个请求、
到了计划时间若正好有空位就直接抢位置（而不是去排队）、预约前先确认账号没有设备占用以省掉一次失败往返。
若确实需要进一步压低时延，可考虑的方向是"缩短单次请求链路"而非"并发轰炸"。
