# U_Autobooking · 浴室自动预约系统

作者：**HEDBS** ｜ 项目地址：https://github.com/HEDBS/U_Autobooking ｜ 许可证：MIT

针对 `h5.hydream.cn`（浴室预约系统）的自动预约工具。
**单个 .py 文件，双击运行，全程菜单操作，无需命令行参数。**

## 一、功能

| 功能 | 说明 |
|---|---|
| 空闲预约 | 监控目标浴室的空闲位置数量，数量满足设定条件时自动完成预约 |
| 排队预约 | 浴室满员进入排队模式时，读取当前排队人数，人数满足条件时自动加入排队，并持续跟踪排队结果，排到位置后报告预约的浴室与位置编号 |
| 结果通知 | 预约成功后可将结果推送到指定命令（消息见环境变量 `HY_DREAM_MSG`） |
| 快速启动 | 配置完成后启动时自动倒计时进入监控，可按键中断 |
| 自检 | 内置 11 项离线自检，含两种完整流程模拟，不联网即可验证 |

## 二、使用流程

1. 双击 `U_Autobooking.py`。
2. 首次运行进入引导配置：账号密码 → 目标浴室 → 空闲触发条件 → 排队设置 → 检测周期。
3. 配置完成后再次启动进入**快速启动**：倒计时结束自动开始监控；倒计时中按 `S` 进入设置菜单，按 `Q` 退出。

主菜单：

```
   1) 启动自动预约监控   （默认）
   2) 取消排队 / 取消预约
   3) 修改运行设置
   4) 系统自检
   5) 退出程序
```

设置菜单包含：账号与密码、目标浴室与设备类型、空闲预约条件、排队自动预约、检测周期与结果通知、启动方式修复。
每进入一个页面会先清屏，界面始终只显示当前操作所需内容。
主菜单与快速启动页会显示**实时状态**：目标浴室当前的空闲/总计，满员时显示当前排队人数（15 秒内复用缓存，避免频繁请求；读取失败会给出提示，不影响操作）。

```
  【主菜单】
--------------------------------------------------------------
   账号：138****0000
   目标浴室：1号楼1层 (男)
   空闲触发：空闲位置 不超过 1 时
   排队触发：排队人数 不超过 2 时
   检测周期：每 6 秒
   实时状态（19:28:13）：空闲 26/28
```

多间浴室时逐行列出；满员时显示为 `已满员（0/28）· 当前排队 3 人`。

## 三、浴室如何选择（初始默认浴室）

站点数据结构为：**校区 → 设备类型 → 浴室（区域） → 位置**。程序的处理方式：

1. **校区**：自动使用账号中保存的校区（`default_org_area_id`）。未绑定校区时会提示先在网页端选择。
2. **设备类型**：列出该校区全部类型（浴室、吹风机等），默认选中「需要预约」的类型。
3. **浴室**：列表同时显示**空闲/总计**，便于直接判断。选择规则：
   - 标记「账号默认」的浴室 —— 网页端设置的默认浴室（`default_device_area_id`），**直接回车即选中它**，这是默认的初始浴室；
   - 没有账号默认时，回车沿用上次选择；
   - 无任何历史记录时，回车选中列表第一项；
   - 可多选，例如输入 `1,3` 同时监控两个浴室，任一满足条件即执行。
4. 选择结果保存至 `U_Autobooking_state.json`，后续无需重复设置；需要变更时进入设置菜单第 2 项。

## 四、触发条件

**空闲预约**：只对"还有空位"的情况生效，按规则决定何时自动预约。设置界面用的是大白话，不再让你去理解 ≤ / ≥ 的符号含义：

| 规则 | 含义 |
|---|---|
| 有空位就预约 | 空闲 ≥ 1，一有空位立刻抢，最积极 |
| 空闲剩 N 个及以下时预约 | 抢最后几个位置（N 一般 1~3） |
| 空闲达到 N 个及以上时预约 | 位置多、人少的时候去 |
| 空闲恰好为 N 个时预约 | — |

N 必须 ≥ 1：填 0 会让规则**恒真**（≥0 永远成立 = 无条件预约）或**恒假**（≤0 只在满员成立，而满员走排队），程序会直接拒绝这种设置并说明原因。

**排队预约**：**只看排队人数，与浴室是否满员无关**。队列越长说明排到得越晚，适合"现在不急着洗、先占个位"的用法。

| 规则 | 含义 |
|---|---|
| 排队人数不超过 N 人时排队 | 队列短、等得少 |
| 排队人数达到 N 人及以上时排队 | 队列长到一定规模才占位 |
| 排队人数恰好为 N 人时排队 | — |

排队阈值允许填 0；浴室满员且总线未返回排队人数时，按"无人排队"处理，此时加入会立刻轮到你。

**两个开关互相独立**，按你当天的情况组合：

| 场景 | 设置 |
|---|---|
| 现在就想洗澡 | 打开「空闲预约」，规则选"空闲剩 N 个及以下"→ 抢在空位消失前拿到位置 |
| 现在不想洗，只想提前占位 | **关闭「空闲预约」**（否则会真的抢到位置，而预约后须在约 5 分钟内到场开机，过期自动取消），只保留「排队预约」 |

**优先级**：只要还有空位且「空闲预约」是开着的，就先按空闲规则抢位置（能直接拿到位置，优于排队）；否则再按排队规则判断。

**动手前先查本人状态**：程序在预约或排队之前，会先确认你的账号当前没有设备
（已预约 / 使用中 / 排队中）。已有设备时不会重复下单，而是直接提示当前占用的位置，
避免被服务器以 `101212 你同时只能使用一台设备` 拒绝。主页面也会显示这一状态。

排队后程序持续跟踪状态，排到位置时报告：**预约是否成功、预约在哪间浴室、几号位置、预约时间**。
可设置排队最长等待时长，超时后返回空闲监控（排队状态保留，可在手机上手工取消）。

检测周期默认 8 秒。周期过短可能触发站点安全策略，建议不低于 5 秒。

## 五、洗澡时间计划（性别 / 时长 / 计划洗澡时间）

设好「计划洗澡时间」后，程序不再只看条件，而是**只在不会提前叫到你的时候动手**：

- **抢空位**：只在 `计划时间 − 到场准备时间` 之后才抢（抢到就必须立刻过去，否则位置会超时取消）
- **排队**：只在 `现在 + 预计等待 ≥ 计划时间 − 到场准备时间` 时才排——**宁可晚排，不早到**

**预计等待优先用站点给的值**（`waitingInfo.expectedWaitingTime`）。实测该站点这个数字与排队人数不成"1 人 1 分钟"：
151 人对应 30 分钟、139 人对应 50 分钟。拿不到时才退回 `排队人数 × 平均时长`，再乘**保守系数**（默认 0.8，
即故意低估等待、更晚排队）。所以不会出现"还没到计划时间，却轮到我"的情况。

### 平均洗澡时长与性别

程序按性别取内置平均时长，作为估算兜底（可随时改写）：

| 性别 | 内置默认 | 依据 |
|---|---|---|
| 男 | 10 分钟 | 北京大学学报（自然科学版）2025《基于混合策略的高校学生生活节水潜力模拟研究》：高校学生每周洗浴 4~6 次，25% 单次超过 20 分钟；新浪天津 2019 洗澡习惯报告：男性平均比女性少约 10 分钟 |
| 女 | 20 分钟 | 同上 |

**性别来源**：优先从账号读取（站点 `getUserInfo` 的 `sex` 字段，1=男 2=女），读不到（保密）时提示你手动指定或按通用值估算。
性别还用于**校验浴室性别限制**——站点每个浴室都有 `gender_limit`，不匹配会直接拦下。

### 预约时间合法性检查

启动监控前（以及保存设置时）会先校验，不合法就直接停：

| 检查项 | 依据 |
|---|---|
| 距离计划时间是否还有足够的到场准备时间 | 你设置的到场准备分钟数 |
| 计划洗澡时长是否超过站点单次上限 | 设备类型的 `max_run_time`（实测该站点为 60 分钟） |
| 浴室性别限制是否与你的性别一致 | 浴室的 `gender_limit`（实测 8 间均为男浴，与账号性别一致） |
| 浴室是否维护/停用/未开放 | 浴室的 `status` 与 `expected_open_time`（会过滤掉站点模板文本误报） |
| 每日预约次数上限 | 设备类型的 `max_reserve_times`（实测为 10 次） |

### 侦测频率

默认 **1 秒 1 次**，可在 1~60 秒之间调整（设置菜单第 6 项）。为压住请求量，程序把每轮压到
**只发 1 个总线请求**（一次性拿到空闲数、排队人数、预计等待、本人状态），失败时不做请求内重试，
改为下一轮再试；被站点安全策略拦截时会自动退避。

## 六、取消机制

排队或预约成功后可以退出，三个入口：

| 场景 | 行为 |
|---|---|
| 手动取消 | 主菜单 `2) 取消排队 / 取消预约`：先显示当前状态（如"排队中：当前排位 136 号"），确认后排队中调 `cancelQueue` 退出队列；已预约/使用中调 `cancelReserve` 释放位置，并复核结果 |
| 排到的时间早于计划 | 若已设计划洗澡时间，排到太早会自动取消该位置并继续等待合适时机（默认开启）。为避免反复消耗每日预约次数，连续自动取消最多 3 次，之后保留位置并提示 |
| 超过计划时间仍未轮到 | 自动退出排队（默认开启），避免占着队列却已不打算去 |

取消后主页面"实时状态"会立刻显示 `已无排队/预约` 作为复核。

## 七、生成文件

| 文件 | 说明 |
|---|---|
| `U_Autobooking_state.json` | 账号密码、选择的浴室、触发条件、登录状态。程序自动维护，无需手工编辑 |
| `U_Autobooking.log` | 运行日志，记录每轮的浴室空闲情况与操作结果 |

登录状态自动复用；失效时使用已保存的账号密码自动重新登录。
两个文件均为本机明文存储，请勿随意外传该目录。

## 八、无人值守运行

计划任务、后台启动（`pythonw`）等无键盘输入的环境下，程序自动跳过菜单，
直接以已保存的配置开始监控，无需任何人工操作。

## 九、排错

菜单第 3 项「系统自检」可离线检查接口解析、触发条件、浴室状态、排队数据、登录状态存取，
以及两种完整流程模拟，不联网、不涉及账号。

| 现象 | 处理 |
|---|---|
| 账号或密码不正确 | 设置菜单第 1 项重新输入 |
| 站点提示"为了保护您的账户安全，请10分钟后重试" | 站点对连续输错密码有 10 分钟限制；无人值守时程序会按提示等待后重试 |
| 请求被网站安全策略拦截 | 通常稍后自动恢复；持续出现请调大检测周期 |
| 101212 你同时只能使用一台设备 | 你的账号已有一台设备（预约中或使用中）。程序会自动识别并跳过重复预约，主页面的"实时状态"能看到当前占用（如 `你 已预约：10#1层 位置 22`）；等该设备结束或先手动停止后再抢 |
| 反复提示登录状态失效 | 设置菜单第 1 项重新输入密码（会清除旧登录状态） |
| 需要完全重新配置 | 删除 `U_Autobooking_state.json` 后重新启动 |
| 双击文件打开的是其他软件 | 设置菜单第 6 项「启动方式修复」 |

## 十、技术说明

站点为 pgel 框架的 H5 应用，接口为 `POST https://lz.hydream.cn/api/v1/<模块>/<动作>`，表单提交。

| 用途 | 接口 | 关键参数 |
|---|---|---|
| 登录 | `UserApi/loginWidthPwd` | `mobile`、`pwd`（返回 `sessionName`/`sessionId`，配合 cookie 维持登录） |
| 账号信息 | `UserApi/getUserInfo` | — |
| 设备类型 | `DeviceAreaApi/selectDeviceTypeByOrgAreaId` | `orgAreaId` |
| 浴室列表与空闲数 | `DeviceAreaApi/selectDeviceAreasWithDeviceState` | `orgAreaId`、`deviceTypeKey`（返回 `idleNum`/`totalNum`） |
| 位置列表 | `DeviceAreaApi/selectDevicesByAreaId` | `deviceAreaId`、`deviceTypeKey`（`device_status=ready` 为空闲） |
| 实时状态总线 | `BusApi/exchangeMsg` | `deviceAreaId`、`deviceTypeKey`、`time`、`lastId`（返回 `waitingInfo` 排队人数、`userState` 本人状态） |
| 加入排队 | `DeviceAreaApi/queueUp` | `deviceAreaId`、`deviceTypeKey`（返回 `result=queued`） |
| 取消排队 | `DeviceAreaApi/cancelQueue` | 同上 |
| 体温登记 | `HealthApi/createLog` | `bodyTemperature`、`deviceTypeKey`（程序会先读取站点设置 `checkBodyTemperature`，仅在该校区确实需要时提交） |
| 预约 | `DeviceApi/reserve` | `uuid`（位置的 `device_key`） |

接口字段做了多命名兼容，站点版本差异一般不会导致失败。
运行环境：Python 3.7 及以上，仅使用标准库。

## 十二、已知取舍：为什么没有实现「暴力模式」

考虑到同时段可能有大量用户抢位置，曾评估过一种"暴力模式"：不等待返回、按固定频率
连续并发发送预约请求，直到成功为止。**当前版本不实现**，原因如下：

| 风险 | 说明 |
|---|---|
| 触发风控 | 站点前置阿里云 WAF，且存在登录频率限制（实测连续失败即被要求等 10 分钟）；并发请求是最容易被识别为攻击的特征 |
| 账号风险 | 高频异常调用可能导致账号被限制或封禁，得不偿失 |
| 无法判定结果 | 不等待返回就发下一次，无法知道哪一次成功，可能同时占住多个位置，触发 `101212 你同时只能使用一台设备`，或白白消耗每日预约次数上限（实测为 10 次） |
| 数据竞争 | 服务端分配位置存在竞态，暴力并发未必比"精准时机 + 高频轮询"命中率更高 |

**更有效的替代做法**（本程序已实现）：把轮询压到 1 秒并在每轮只发 1 个请求、
在触发瞬间优先直接抢空位（而不是排队）、预约前先确认账号没有设备占用以省掉一次失败往返。
若确实需要进一步压低时延，可考虑的方向是"缩短单次请求链路"而非"并发轰炸"。
